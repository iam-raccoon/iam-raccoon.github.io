> 로봇을 2대로 늘리니 20분 시점 발견 인원이 4.5 → 6.5명이 됐다. 그런데 **누워 있는 조난자**는 1대든 2대든 자꾸 놓쳤다. 이틀 동안 파라미터 다섯 개를 돌려도 안 움직였는데, 로봇을 누운 사람 앞에 세우고 화면을 저장해 보니 **신발과 다리만** 찍혀 있었다. 카메라를 0.10 rad 숙이자 30분 안 7명 전원 발견이 22 % → **82 % · 90 %**가 됐다.
{: .prompt-info }

## 2대로 늘리기 : 네임스페이스 함정

같은 로봇 두 대를 띄우려면 토픽과 좌표계 이름 앞에 `ugv1/` · `ugv2/` 를 붙여야 한다. 세 번 연달아 밟았다.

1. 로봇 모델 발행기가 좌표 변환을 **전역** `/tf_static` 에 내서 SLAM 이 `ugv1/laser_frame` 을 못 찾음
2. 좌표 변환 구독기도 전역 `/tf` 를 구독함
3. 두 지도를 잇는 변환을 전역에 내서, **1대 구성에서도** 목표 11번 중 10번 실패

> 커밋에 남긴 교훈 : "2대를 의심하기 전에 같은 런치로 1대부터 돌렸어야 했다."
{: .prompt-tip }

**지도 합치기 오프셋.** 두 로봇의 지도를 합칠 때 출발 위치 차이만큼 밀었다. 그런데 시뮬레이터의 위치는 이미 월드 기준이라 오프셋은 0 이어야 했다. 한쪽이 벽이라고 본 칸을 다른 쪽 지도에서 찾아보니 판단 가능한 521칸 중 **99.2 % 가 모순**이었다.

**박힘 오판.** 2대가 1,400초 동안 0명을 찾았다. 로봇이 '박혔다' 고 판단한 게 82번인데, Nav2 가 스스로 하는 복구 동작 (제자리 회전 · 후진 · 대기) 을 박힘으로 본 것이었다. 명령 속도 기준으로 바꾸니 0번. 1.6 m 간격으로 나란히 출발시킨 것도 문제였다 — 서로의 안전 여유 (0.55 m) 안이라 **둘 다 갇혔다** (목표 245번 중 243번 실패). 앞뒤 6 m 로 띄웠다.

이걸 다 고치니 **2대가 1대를 이긴다** : 1,200초 시점 발견 인원 4.5 → 6.5명, 짝지어 비교한 4쌍 모두 2대 승.

## 같은 결함을 여섯 번 맞았다

"탐사 끝" 판정이 자꾸 너무 일찍 또는 영원히 안 났다. 원인을 하나 고치면 비슷한 다른 게 나왔다.

- 너무 작은 미관측 자투리
- 맵 범위 밖 경계
- 크기 하한보다 작은 경계
- 다가갈 자리가 없는 경계
- 이미 가 봤던 경계
- 구역을 나눈 뒤 생긴 미관측

모두 **"목표를 고르는 쪽이 손댈 수 없는 것을, 완료 판정은 세고 있다"**는 같은 결함이었다. 커밋에 이렇게 적었다 — "애초에 목표 고르는 함수의 `continue` 문을 전부 세어 보고 판정을 그에 맞췄으면 한 번에 끝났다."

## 이틀을 쓴 뒤에야 화면을 봤다

누운 사람을 놓치는 걸 고치려고 파라미터 다섯 개 (방향 수 · 유령 필터 · 방 보너스 · 누움 판정 완화 · 검출 신뢰도) 를 이틀 동안 돌렸다. 아무것도 움직이지 않았다.

놓친 판을 다시 보니 "판정에서 떨어짐" 은 0건이고, 거의 전부 **"후보로 잡힌 적조차 없음"**이었다. 로봇을 누운 사람 2 m 앞에 세우고 카메라 화면을 저장했다. **신발과 다리만** 찍혀 있었다.

| | 값 |
|---|---|
| 카메라 높이 | 0.5 m |
| 수직 화각 | 48.9° |
| 수평 조준일 때 화면 아래 끝이 바닥에 닿는 거리 | **1.10 m** |
| 0.10 rad 숙였을 때 | 0.86 m |

카메라가 너무 정면을 보고 있어서, 가까이 누운 사람의 상체가 화면 아래로 빠져나갔다. 인식기가 아니라 **기하** 문제였다.

| 포탑 숙임 | 누운 3명 발견률 | 최소 검출 거리 |
|---|---:|---:|
| 0 (수평) | 52 % | 2.0 m |
| 0.20 rad | 78 % | 1.3 m |
| **0.10 rad** | 누움 18 / 18 | |

0.10 · 0.20 · 0.30 rad 를 비교해 0.10 을 골랐다. 처음에 "효과 없음" 으로 껐던 '여러 방향에서 봐야 확인' 옵션도, 검출 병목이 풀린 뒤 다시 켜니 효과가 있었다 (4 / 4 vs 2 / 4).

```python
SEEN_DIRS = int(os.environ.get('UGV_SEEN_DIRS', '2'))
SEARCH_PITCH = float(os.environ.get('UGV_SEARCH_PITCH', '0.10'))
```

LiDAR 에는 누운 사람 · 휠체어 · 침상이 장애물로 안 잡혀서 (높이가 스캔 면 아래), 깊이 카메라 점군을 장애물 입력에 더했다.

```yaml
depth:
  topic: /camera/points
  min_obstacle_height: 0.08   # 바닥을 장애물로 찍지 않게
  max_obstacle_height: 1.60
  obstacle_max_range: 6.0     # 깊이는 멀수록 부정확
```

## 결과 : 30분 안 7명 전원

| 설정 | 30분 안 7 / 7 완주율 |
|---|---:|
| 포탑 수평 | 22 % |
| 0.20 rad | 67 % |
| **0.10 rad + 두 방향 확인** | **82 % · 90 %** |

마지막 줄은 유효 50판짜리 검증을 두 번 따로 돌린 값이다 (95 % 신뢰구간 69 ~ 90 % / 79 ~ 96 %). 두 번의 로깅 코드가 조금 달라서 합쳐 86 % 로 쓰지 않고 따로 적었다. 1대 구성도 같이 빨라져서 7 / 7 까지 걸린 시간 중앙값이 57분 → 26분.

## 마지막 한 명은 시간 문제였다

끝까지 가끔 놓치는 한 명이 있었다. 남서쪽 방 깊숙한 곳 (y < −11) 까지 내려간 판은 34판 중 33판이 찾았고, 못 내려간 판은 6판 중 0판. **알고리즘이 아니라 시간 예산**이었다. 제한을 45분으로 늘리니 11판 모두 찾았다.

| 제한 시간 | 20분 | 25분 | 30분 | 35분 | 40분 이상 |
|---|---:|---:|---:|---:|---:|
| 7 / 7 완주율 | 56 % | 77 % | 86 % | 91 % | 91 % |

## 작은 표본에 속을 뻔한 것들

- '누움 판정 완화' 는 처음 4 / 4 vs 1 / 4 로 압승이었다. 그런데 조건과 머신이 묶여 있었다. 머신을 바꿔 돌리니 뒤집혔다 (합계 7 / 8 vs 4 / 7, p = 0.23)
- '먼 방 가중치' 는 21판 시점 44 % vs 83 % → 41판에서 62 % vs 65 %
- '방 단위로 마저 훑기' 는 라운드마다 45 % ↔ 90 % 로 뒤집혔다

그래서 이 뒤로는 조건을 한 머신 안에서 번갈아 돌리고, 판 수를 미리 정해 두고, 두 머신에서 재현돼야 채택했다 ([④편]({% post_url 2026-09-05-ugv-04-scaling %})).
