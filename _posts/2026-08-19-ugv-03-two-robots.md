> 로봇을 2대로 늘리니 20분 시점 발견 인원이 4.5명에서 6.5명이 됨. 그런데 누워 있는 조난자는 1대든 2대든 자꾸 놓쳤음. 이틀 동안 파라미터 다섯 개를 돌려도 그대로였는데, 로봇을 누운 사람 앞에 세우고 화면을 저장해 보니 신발과 다리만 찍혀 있었음. 카메라를 0.10 rad 숙이자 30분 안에 7명을 전원 발견하는 비율이 22 %에서 82 %, 90 %로 올랐음.
{: .prompt-info }

## 2대로 늘리며 밟은 네임스페이스 함정

같은 로봇 두 대를 띄우려면 토픽과 좌표계 이름 앞에 `ugv1/`, `ugv2/`를 붙여야 함. 여기서 세 번 연달아 걸렸음.

1. 로봇 모델 발행기가 좌표 변환을 전역 `/tf_static`에 내서 SLAM이 `ugv1/laser_frame`을 못 찾았음
2. 좌표 변환 구독기도 전역 `/tf`를 구독했음
3. 두 지도를 잇는 변환을 전역에 내서, 1대 구성에서도 목표 11번 중 10번 실패했음

커밋에는 "2대를 의심하기 전에 같은 런치로 1대부터 돌렸어야 했다"고 적어 뒀음.

두 로봇의 지도를 합칠 때는 출발 위치 차이만큼 오프셋을 줬음. 그런데 시뮬레이터의 위치는 이미 월드 기준이라 오프셋은 0이어야 했음. 한쪽이 벽이라고 본 칸을 다른 쪽 지도에서 찾아보니, 판단 가능한 521칸 중 99.2 %가 모순이었음.

박힘 판정도 틀려 있었음. 2대가 1,400초 동안 0명을 찾았는데, 로봇이 박혔다고 판단한 게 82번이었음. Nav2가 스스로 하는 복구 동작(제자리 회전, 후진, 대기)을 박힘으로 본 것임. 명령 속도 기준으로 바꾸니 0번이 됨. 1.6 m 간격으로 나란히 출발시킨 것도 문제였음. 서로의 안전 여유(0.55 m) 안이라 둘 다 갇혔고, 목표 245번 중 243번 실패함. 앞뒤로 6 m 띄워 출발시켰음.

이걸 다 고치자 2대가 1대를 이겼음. 1,200초 시점 발견 인원이 4.5명에서 6.5명이 됐고, 짝지어 비교한 4쌍 모두 2대가 앞섰음.

## 같은 결함을 여섯 번 만났음

탐사 끝 판정이 자꾸 너무 일찍 나거나 영원히 안 났음. 원인을 하나 고치면 비슷한 다른 원인이 나왔음.

- 너무 작은 미관측 자투리
- 맵 범위 밖 경계
- 크기 하한보다 작은 경계
- 다가갈 자리가 없는 경계
- 이미 가 봤던 경계
- 구역을 나눈 뒤 생긴 미관측

여섯 개 모두 목표를 고르는 쪽이 손댈 수 없는 것을 완료 판정에서는 세고 있었음. 커밋에는 "애초에 목표 고르는 함수의 `continue` 문을 전부 세어 보고 판정을 그에 맞췄으면 한 번에 끝났다"고 적었음.

## 이틀을 쓴 뒤에야 화면을 봤음

누운 사람을 놓치는 문제를 고치려고 파라미터 다섯 개(방향 수, 유령 필터, 방 보너스, 누움 판정 완화, 검출 신뢰도)를 이틀 동안 돌렸음. 결과는 달라지지 않았음.

놓친 판을 다시 보니 판정에서 떨어진 경우는 0건이고, 거의 전부 후보로 잡힌 적조차 없었음. 로봇을 누운 사람 2 m 앞에 세우고 카메라 화면을 저장했더니 신발과 다리만 찍혀 있었음.

카메라 높이는 0.5 m, 수직 화각은 48.9°임. 수평으로 조준하면 화면 아래 끝이 1.10 m 앞 바닥에 닿고, 0.10 rad 숙이면 0.86 m가 됨. 카메라가 너무 정면을 보고 있어서 가까이 누운 사람의 상체가 화면 아래로 빠져나간 것임. 인식기 문제가 아니라 카메라 기하 때문이었음.

| 포탑 숙임 | 누운 3명 발견률 | 최소 검출 거리 |
|---|---:|---:|
| 0 (수평) | 52 % | 2.0 m |
| 0.20 rad | 78 % | 1.3 m |
| 0.10 rad | 누움 18/18 | |

0.10, 0.20, 0.30 rad를 비교해 0.10을 골랐음. 처음에 효과가 없다고 껐던 '여러 방향에서 봐야 확인' 옵션도, 검출 병목이 풀린 뒤 다시 켜니 효과가 있었음 (4/4 vs 2/4).

```python
SEEN_DIRS = int(os.environ.get('UGV_SEEN_DIRS', '2'))
SEARCH_PITCH = float(os.environ.get('UGV_SEARCH_PITCH', '0.10'))
```

누운 사람, 휠체어, 침상은 높이가 스캔 면 아래라 LiDAR에 장애물로 잡히지 않음. 그래서 깊이 카메라 점군을 장애물 입력에 더함.

```yaml
depth:
  topic: /camera/points
  min_obstacle_height: 0.08   # 바닥을 장애물로 찍지 않게
  max_obstacle_height: 1.60
  obstacle_max_range: 6.0     # 깊이는 멀수록 부정확
```

## 결과: 30분 안에 7명 전원

| 설정 | 30분 안 7/7 완주율 |
|---|---:|
| 포탑 수평 | 22 % |
| 0.20 rad | 67 % |
| 0.10 rad + 두 방향 확인 | 82 %, 90 % |

마지막 줄은 유효 50판짜리 검증을 두 번 따로 돌린 값임 (95 % 신뢰구간 69~90 %, 79~96 %). 두 번의 로깅 코드가 조금 달라서 합친 86 %로 쓰지 않고 따로 적었음. 1대 구성도 같이 빨라져서 7/7까지 걸린 시간 중앙값이 57분에서 26분으로 줄었음.

## 마지막 한 명은 시간 문제였음

끝까지 가끔 놓치는 한 명이 있었음. 남서쪽 방 깊숙한 곳(y < −11)까지 내려간 판은 34판 중 33판이 찾았고, 못 내려간 판은 6판 중 0판이었음. 알고리즘 문제가 아니었음. 시간 예산이 모자랐음. 제한을 45분으로 늘리니 11판 모두 찾았음.

| 제한 시간 | 20분 | 25분 | 30분 | 35분 | 40분 이상 |
|---|---:|---:|---:|---:|---:|
| 7/7 완주율 | 56 % | 77 % | 86 % | 91 % | 91 % |

## 작은 표본에 속을 뻔한 것들

- '누움 판정 완화'는 처음에 4/4 vs 1/4로 크게 이겼음. 그런데 조건과 머신이 묶여 있었고, 머신을 바꿔 돌리니 뒤집혔음 (합계 7/8 vs 4/7, p = 0.23)
- '먼 방 가중치'는 21판 시점에 44 % vs 83 %였다가 41판에서는 62 % vs 65 %가 됐음
- '방 단위로 마저 훑기'는 라운드마다 45 %와 90 %로 번갈아 뒤집혔음

그래서 이 뒤로는 조건을 한 머신 안에서 번갈아 돌리고, 판 수를 미리 정해 두고, 두 머신에서 재현돼야 채택함 ([④편]({% post_url 2026-09-05-ugv-04-scaling %})).
