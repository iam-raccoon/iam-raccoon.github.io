[③편]({% post_url 2026-07-30-vtol-03-receding %}) 끝에서 경로점 4만 매번 같은 만큼 빗나간다는 것을 확인했다. 이번 글은 그 원인을 찾아 경로 생성기를 바꾼 기록이다.

## 경로점 4 오차

경로점 4는 런마다 흔들리지 않고 매번 6~6.5m를 비슷하게 질렀다. 같은 자리에서 같은 방향으로 같은 만큼 빗나가니 우연으로 볼 수 없었고, 구조에서 나오는 오차였다.

하지만 그동안 고친 것은 전부 팔로워(경로 추종기) 쪽이었다.

- 실측 오차를 거꾸로 넣기([②편]({% post_url 2026-07-29-vtol-02-determinism %}))
- 경로점마다 다시 그리기, 시작점 평균([③편]({% post_url 2026-07-30-vtol-03-receding %}))
- lookahead 거리, 코너 감속, 다른 유도법 이식(전부 실패)

## 곡률 불연속

Dubins 경로는 직선과 최소 반경 원호로 이루어진다. 직선의 곡률은 0, 원호의 곡률은 1/R이다. 그래서 둘의 경계에서 곡률이 0에서 1/R로 한순간에 뛴다.

자동차라면 핸들을 빨리 꺾으면 된다. 하지만 고정익은 선회하려면 먼저 기울어야(롤) 하고, 기우는 데 시간이 걸린다. 경로는 지금부터 원을 그리라고 하는데 비행기는 아직 직선으로 날고 있다. 그 사이에 바깥으로 밀리고, 밀린 만큼 코너를 질러서 경로점을 놓친다.

결국 원인은 경로의 곡률 불연속이었다. ③편에서 시뮬레이터 쪽 한계로 보고 넘겼던 오차다.

## Catmull-Rom 스플라인

그래서 각 경로점을 정확히 지나면서 곡률이 매끈하게 변하는 곡선으로 바꿨다. centripetal Catmull-Rom 스플라인(α = 0.5)은 급한 코너에서도 튀어 나가거나 뾰족하게 꺾이지 않는다.

아래는 `dubins_path.py`에 새로 짠 생성기 본체다.

```python
def wp_sequence_to_spline_points(waypoints, r_min, step_m=8.0,
                                 initial_heading_math=math.pi / 2,
                                 free_final_heading=False):
    """(north,east) WP 리스트 → 곡률연속 스플라인 dense 점 리스트."""
    W = [(float(w[0]), float(w[1])) for w in waypoints]
    if len(W) < 2:
        return list(W)

    # 팬텀 시작점 : W0 뒤쪽 (−initial_heading) → W0 접선이 현재 기수와 정렬
    d0 = math.hypot(W[1][0] - W[0][0], W[1][1] - W[0][1]) or 1.0
    p_start = (W[0][0] - d0 * math.cos(initial_heading_math),
               W[0][1] - d0 * math.sin(initial_heading_math))
    # 팬텀 끝점 : 마지막 구간 외삽
    p_end = (2 * W[-1][0] - W[-2][0], 2 * W[-1][1] - W[-2][1])

    P = [p_start] + W + [p_end]
    alpha = 0.5                               # centripetal

    def _tnext(ti, a, b):
        d = math.hypot(b[0] - a[0], b[1] - a[1])
        return ti + max(d, 1e-6) ** alpha

    out = [W[0]]
    for i in range(1, len(P) - 2):            # 구간 W[i-1] → W[i]
        p0, p1, p2, p3 = P[i - 1], P[i], P[i + 1], P[i + 2]
        t0 = 0.0
        t1 = _tnext(t0, p0, p1)
        t2 = _tnext(t1, p1, p2)
        t3 = _tnext(t2, p2, p3)
        n = max(1, int(math.hypot(p2[0] - p1[0], p2[1] - p1[1]) / step_m))
        for s in range(1, n + 1):
            t = t1 + (t2 - t1) * (s / n)
            out.append(_cr_point(p0, p1, p2, p3, t, t0, t1, t2, t3))
    out[-1] = W[-1]                           # 끝점 정확히 고정
    return out
```

`_cr_point`는 Barry-Goldman 방식으로 한 점을 계산하는 보조 함수다(선형 보간 다섯 번). 외부 라이브러리 없이 `math`만 쓴다. 타입 표기와 `initial_heading`이 없을 때의 분기는 생략했다.

경로를 쓰는 곳은 ③편에서 하나로 모아 둔 `_build_path`뿐이라 여기만 고치면 되었다(`fw_navigator.py`).

```python
def _build_path(self, wps, r_min, step_m=8.0,
                initial_heading_math=math.pi / 2,
                free_final_heading=False):
    """경로 생성 디스패처 : FW_PATH_MODE 로 Dubins / 스플라인 선택 (v6.0).
    팔로워 (carrot) · 천이 · WP 판정은 무손 — dense (n,e) 점 리스트 포맷 동일."""
    fn = (wp_sequence_to_spline_points if FW_PATH_MODE == 'spline'
          else wp_sequence_to_dubins_points)
    return fn(wps, r_min, step_m=step_m,
              initial_heading_math=initial_heading_math,
              free_final_heading=free_final_heading)
```

새 생성기는 기존 Dubins 생성기와 입출력을 똑같이 맞췄다. 덕분에 팔로워와 천이, 경로점 판정, 경로점마다 다시 그리기는 하나도 건드리지 않고 경로 생성만 바꿀 수 있었다. 출발점 뒤에는 가상의 점을 하나 두어 곡선의 시작 방향이 지금 기수 방향과 맞게 했고, 그래서 경로점마다 다시 그릴 때도 이어지는 부분이 부드럽다. 설정 한 줄(`FW_PATH_MODE = 'spline' | 'dubins'`)로 언제든 되돌릴 수도 있다.

## 결과

같은 PC에서 두 경로를 번갈아 돌렸다. 단위는 m다.

| | 경로점 2 | 경로점 3 | 경로점 4 | 경로점 5 |
|---|---:|---:|---:|---:|
| Dubins 1번째 | 0.7 | 2.8 | 6.5 | 4.7 |
| Dubins 2번째 | 0.7 | 2.6 | 6.0 | 3.6 |
| 스플라인 1번째 | 0.8 | 0.6 | 0.9 | 3.1 |
| 스플라인 2번째 | 0.7 | 0.5 | 4.1 | 9.5 |

스플라인 1번째 런은 경로점 2, 3, 4가 모두 1m 미만이었다. 지금까지 갈 때 구간에서 나온 최고 기록이고, 트레이도 0.12m로 집었다. 경로점 3은 두 번 모두 2.6~2.8m에서 0.5~0.6m로 일관되게 좋아졌다. 스플라인이 급한 코너에서 최소 선회 반경보다 급한 곡률을 요구해 발산하지 않을까 걱정했는데, 실제 코스(24° 코너)에서는 그런 일이 생기지 않았다.

다만 비교가 두 번씩뿐이고, 스플라인 2번째 런은 경로점 4가 4.1m, 경로점 5가 9.5m로 흔들렸다. 그 PC의 통신 타이밍 편차로 보고 있지만, 여러 런의 통계와 실기체 검증으로 더 확인할 필요가 있다. 마지막 긴 구간(경로점 5)은 스플라인 끝점 처리 때문에 개선 여부가 아직 애매하다.
