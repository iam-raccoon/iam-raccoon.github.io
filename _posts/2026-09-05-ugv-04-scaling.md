> 1대 → 2대는 확실한 이득이었다 (10분 시점 발견 인원 3 → 6명). 그런데 3대는 네 가지 크기의 맵 어디서도 2대를 이기지 못했다. 원인은 로봇끼리 길을 막는 게 아니라 **Nav2 경로 탐색의 실패 루프** 였고, 3대일 때 로봇 하나하나가 그 루프에 더 잘 빠졌다. 고치니 격차는 거의 사라졌지만 뒤집히지는 않았다. 권장 구성은 **2대**.
{: .prompt-info }

## 맵 네 개

| 맵 | 크기 | 조난자 | 제한 시간 |
|---|---|---:|---:|
| 작은 맵 | 28 × 20 m | 3 | |
| 큰 맵 | 56 × 40 m | 7 | 30분 |
| XL | 84 × 40 m | 13 | 45분 |
| XXL | 168 × 40 m (방 32개) | 34 | 90분 |

## 첫 번째 3대 : 출발 위치부터 틀렸다

3대를 처음 붙였을 때 출발 위치가 −12 / 0 / +12 m 로 고정돼 있었다. XL 맵의 담당 구역은 [−41, −13.7] / [−13.7, 13.7] / [13.7, 41] 이라, 양 끝 로봇이 **자기 구역 밖에서 출발해** 27 m 를 건너가야 했다. 구역 경계에서 계산하게 바꿨다 (−27.3 / 0 / +27.3).

> **조용한 고장** — XL 맵을 생성할 때 월드 파일 안의 이름이 파일명과 다르면, 로봇 생성 서비스는 "OK" 를 돌려주고 **로봇만 안 들어간다**.
{: .prompt-warning }

## 중앙값으로는 안 보였다

XL 에서 유효 85판, 45분 평균 발견 인원 : 1대 10.6 / **2대 12.1** / 3대 11.3.

처음엔 중앙값만 봤는데 2대와 3대가 네 시점 모두 같았다. 발견 인원이 0 ~ 13 의 정수라 한 명 차이가 중앙값에서는 묻힌다. 평균을 보니 후반에 갈렸다.

이유를 찾으며 기각한 설명이 넷이다.

| 가설 | 확인 | 결과 |
|---|---|---|
| 3대일 때 로봇이 느리다 | 실제 속도 측정 | 둘 다 0.500 m/s |
| CPU 가 모자라다 | 제어 주기 놓친 횟수 | 로봇당 1.55회, 무시할 수준 |
| 시뮬 시간을 덜 받았다 | 받은 시뮬 시간 | 2,650 vs 2,643초 |
| 구역 나누기가 불리하다 | 구역별 누락 | 서 +19 / 중 +27 / 동 +27 %p, 고르게 퍼짐 |

## 진짜 원인 : 경로 탐색 실패 루프

로봇별로 Nav2 가 목표를 포기 (Abort) 한 횟수를 셌다.

| | 2대 | 3대 |
|---|---:|---:|
| 로봇당 포기 횟수 | 23.6 | **51.0** |
| 실패 루프 (포기 100회 이상) 에 빠진 로봇 | 1.9 % | **7.7 %** |
| 그런 로봇이 하나라도 있는 판 | 4 % | **23 %** |

로봇이 독립이라면 3대 중 하나라도 빠질 확률은 `1 − (1 − 0.019)³ = 5.6 %` 여야 한다. 실제는 23 %. 로봇이 많아서 확률이 쌓인 게 아니라 **로봇 하나하나가 더 위험해진** 것이다.

```text
xl3_3_13.log  206  54  64   <- 한 대만 무너짐
```

포기한 뒤 아무것도 안 하고 서 있던 시간도 쟀다. 2대는 판당 2.7분 (한 번에 60초), 3대는 **9.9분** (한 번에 101초).

## 포기를 알아채고 바로 다음 목표로

Nav2 가 목표를 포기하면 바로 다른 목표를 고르고, 연속으로 포기하면 빠져나오게 했다.

```python
if sent_t is None or now - sent_t < grace_s:
    return 'ignore'
if streak + 1 >= max_streak:
    return 'escape'
return 'retarget'
```

> **포기가 아닌 포기** — 처음엔 '포기됨 (ABORTED)' 상태를 그대로 믿었다. 그런데 Nav2 는 **우리가 목표를 바꿔 끼울 때도** 밀려난 옛 목표를 ABORTED 로 끝낸다. 진짜 포기가 0번인 로봇이 헛되이 목표를 4번 바꾸고 1번 후진했다. "포기된 목표가 가장 최근에 보낸 것일 때만 진짜" 로 고쳤다.
{: .prompt-warning }

검증은 한 로봇의 차체 크기를 일부러 3 × 3 m 로 키워 길을 못 찾게 만드는 식으로 했다 (반응 0.75 s · 0.29 s).

| | 고치기 전 | 고친 뒤 |
|---|---:|---:|
| 포기 후 서 있던 시간 (한 번에) | 60 ~ 101초 | 1초 이하 |
| XL 45분, 3대 − 2대 | −0.64명 | −0.17명 (p = 0.03) |

격차는 거의 사라졌지만 3대가 앞서지는 않았다. XXL (168 × 40 m) 에서도 두 머신 모두 **모든 시점에서 2대가 앞섰다** (예 : 10분 9.0 vs 6.1명, 90분 32.5 vs 30.8명). 권장 구성은 그대로 2대다.

## 8판에서 보인 것은 52판에서 사라졌다

판 수가 8 · 10판이었을 때는 "3대가 초 · 중반에 앞선다" 로 읽혔다. 52 · 49판까지 늘리니 사라졌다 (10분 시점 +0.63, p = 0.10 → +0.42, p = 0.17). 판마다 흩어짐이 1.5 ~ 1.7명이라 몇 판으로는 아무것도 말할 수 없다.

재현용 머신에서는 XL 2대 · 3대가 동률 (11.9 vs 11.9) 이었다. 표본을 2대 4판 · 3대 3판으로 세어서 의아했는데, 로그 이름 접두사를 빠뜨린 것이고 실제로는 16 · 15판이었다. 규칙 ("두 머신에서 재현돼야 채택") 대로 잠정 결론으로 두었다가, XXL 에서 두 머신이 일치해 확정했다.

## 300판 넘게 돌리며 정한 측정 규칙

- 조건은 **한 머신 안에서 번갈아** 돌리고, 라운드마다 순서를 바꾼다
- 조건은 파라미터로만 가른다. 다시 빌드하지 않는다
- 판 사이에 남은 프로세스까지 정리한다 — 안 하면 이전 판의 노드가 쌓인다
- "유효 N판이 찰 때까지" 돌린다. 2대 판의 15 % 는 한 대의 카메라가 조용히 죽은 무효 판이었다
- 지표는 "전원 발견 시각" 이 아니라 **"정해진 시점의 발견 인원"**. 전원 발견 시각은 같은 조건에서 700초도 2,672초도 나온다

그 밖에 속을 뻔한 것들.

- 빈 런치 인자 하나 때문에 한쪽 조건이 아예 안 떴는데, 결과가 "유령 0건" 으로 나와 좋은 결과로 읽을 뻔했다
- 정답 좌표를 사람 모델의 발밑으로 잡아서, 누운 사람만 오차가 1.12 · 1.41 m 로 보였다. 몸 중심으로 고치니 0.32 · 0.54 m
- 카메라 RGB 8.7 Hz 와 깊이 11.2 Hz 가 어긋나서, 둘을 짝짓는 동기화기가 **한 번도 짝을 못 지었다**. 로봇이 조용히 눈이 멀어 있었다

## 돌아보면

- 가장 크게 움직인 건 알고리즘이 아니라 **카메라를 0.10 rad 숙인 것** 과 **시간 예산**이었다
- 로봇을 늘리는 건 1 → 2대까지가 확실한 이득이고, 그 뒤는 경로 탐색이 버티는지에 달렸다
- 한두 판짜리 결과는 몇 번이나 뒤집혔다. 판 수를 미리 정하고 두 곳에서 재현하는 습관이 가장 쓸모 있었다
