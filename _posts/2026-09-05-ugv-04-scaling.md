> 1대에서 2대로 늘린 건 확실한 이득이었음 (10분 시점 발견 인원 3명에서 6명). 그런데 3대는 네 가지 크기의 맵 어디서도 2대를 이기지 못했음. 원인은 로봇끼리 길을 막은 게 아니었음. Nav2 경로 탐색의 실패 루프였고, 3대일 때 로봇 하나하나가 그 루프에 더 잘 빠졌음. 고치니 격차는 거의 사라졌지만 뒤집히지는 않았음. 권장 구성은 2대임.
{: .prompt-info }

## 맵 네 개

| 맵 | 크기 | 조난자 | 제한 시간 |
|---|---|---:|---:|
| 작은 맵 | 28 × 20 m | 3 | |
| 큰 맵 | 56 × 40 m | 7 | 30분 |
| XL | 84 × 40 m | 13 | 45분 |
| XXL | 168 × 40 m (방 32개) | 34 | 90분 |

## 처음 붙인 3대는 출발 위치부터 틀렸음

3대를 처음 붙였을 때 출발 위치가 −12, 0, +12 m로 고정돼 있었음. XL 맵의 담당 구역은 [−41, −13.7], [−13.7, 13.7], [13.7, 41]이라서, 양 끝 로봇이 자기 구역 밖에서 출발해 27 m를 건너가야 했음. 출발 위치를 구역 경계에서 계산하게 바꿨음 (−27.3, 0, +27.3).

> XL 맵을 생성할 때 월드 파일 안의 이름이 파일명과 다르면, 로봇 생성 서비스는 "OK"를 돌려주고 로봇만 안 들어감. 에러는 나지 않음.
{: .prompt-warning }

## 중앙값으로는 차이가 안 보였음

XL에서 유효 85판을 돌린 45분 시점 평균 발견 인원은 1대 10.6명, 2대 12.1명, 3대 11.3명임.

처음에는 중앙값만 봤는데, 2대와 3대가 네 시점 모두 같았음. 발견 인원이 0~13의 정수라서 한 명 차이가 중앙값에서는 묻힘. 평균을 보니 후반에 차이가 났음.

이유를 찾으면서 기각한 설명이 넷임.

| 가설 | 확인 | 결과 |
|---|---|---|
| 3대일 때 로봇이 느리다 | 실제 속도 측정 | 둘 다 0.500 m/s |
| CPU가 모자라다 | 제어 주기 놓친 횟수 | 로봇당 1.55회, 무시할 수준 |
| 시뮬 시간을 덜 받았다 | 받은 시뮬 시간 | 2,650 vs 2,643초 |
| 구역 나누기가 불리하다 | 구역별 누락 | 서 +19, 중 +27, 동 +27 %p로 고르게 퍼짐 |

## 원인은 경로 탐색 실패 루프

로봇별로 Nav2가 목표를 포기(Abort)한 횟수를 셌음.

| | 2대 | 3대 |
|---|---:|---:|
| 로봇당 포기 횟수 | 23.6 | 51.0 |
| 실패 루프(포기 100회 이상)에 빠진 로봇 | 1.9 % | 7.7 % |
| 그런 로봇이 하나라도 있는 판 | 4 % | 23 % |

로봇이 서로 독립이라면 3대 중 하나라도 빠질 확률은 `1 − (1 − 0.019)³ = 5.6 %`여야 함. 실제는 23 %였음. 로봇 수가 늘어 확률이 쌓인 것만으로는 설명이 안 됨. 로봇 하나하나가 루프에 더 잘 빠졌음.

```text
xl3_3_13.log  206  54  64   <- 한 대만 무너짐
```

포기한 뒤 아무것도 안 하고 서 있던 시간도 쟀음. 2대는 판당 2.7분(한 번에 60초), 3대는 9.9분(한 번에 101초)이었음.

## 포기를 알아채면 바로 다음 목표로

Nav2가 목표를 포기하면 바로 다른 목표를 고르고, 연속으로 포기하면 빠져나오게 함.

```python
if sent_t is None or now - sent_t < grace_s:
    return 'ignore'
if streak + 1 >= max_streak:
    return 'escape'
return 'retarget'
```

> 처음에는 '포기됨(ABORTED)' 상태를 그대로 믿었음. 그런데 Nav2는 우리가 목표를 바꿔 끼울 때도 밀려난 옛 목표를 ABORTED로 끝냄. 그래서 진짜 포기가 0번인 로봇이 쓸데없이 목표를 4번 바꾸고 1번 후진했음. 포기된 목표가 가장 최근에 보낸 목표일 때만 진짜 포기로 보도록 고침.
{: .prompt-warning }

검증은 한 로봇의 차체 크기를 일부러 3 × 3 m로 키워 길을 못 찾게 만드는 식으로 했음 (반응 0.75 s, 0.29 s).

| | 고치기 전 | 고친 뒤 |
|---|---:|---:|
| 포기 후 서 있던 시간 (한 번에) | 60~101초 | 1초 이하 |
| XL 45분, 3대 − 2대 | −0.64명 | −0.17명 (p = 0.03) |

격차는 거의 사라졌지만 3대가 앞서지는 않았음. XXL(168 × 40 m)에서도 두 머신 모두 모든 시점에서 2대가 앞섰음 (예: 10분 9.0 vs 6.1명, 90분 32.5 vs 30.8명). 권장 구성은 그대로 2대임.

## 8판에서 보인 차이가 52판에서 사라졌음

판 수가 8판, 10판일 때는 3대가 초중반에 앞서는 것처럼 보였음. 52판, 49판까지 늘리니 그 차이가 사라졌음 (10분 시점 +0.63, p = 0.10에서 +0.42, p = 0.17로). 판마다 흩어짐이 1.5~1.7명이라 몇 판으로는 아무것도 말할 수 없음.

재현용 머신에서는 XL 2대와 3대가 동률(11.9 vs 11.9)이었음. 표본을 2대 4판, 3대 3판으로 세어서 이상했는데, 로그 이름 접두사를 빠뜨린 탓이었고 실제로는 16판, 15판이었음. "두 머신에서 재현돼야 채택"이라는 규칙대로 잠정 결론으로 두었다가, XXL에서 두 머신 결과가 일치해 확정함.

## 300판 넘게 돌리며 정한 측정 규칙

- 조건은 한 머신 안에서 번갈아 돌리고, 라운드마다 순서를 바꿈
- 조건은 파라미터로만 가름. 다시 빌드하지 않음
- 판 사이에 남은 프로세스까지 정리함. 안 하면 이전 판의 노드가 쌓임
- 유효 N판이 찰 때까지 돌림. 2대 판의 15 %는 한 대의 카메라가 조용히 죽은 무효 판이었음
- 지표는 전원 발견 시각 대신 정해진 시점의 발견 인원으로 잡음. 전원 발견 시각은 같은 조건에서 700초도, 2,672초도 나옴

그 밖에 속을 뻔한 것들도 있었음.

- 빈 런치 인자 하나 때문에 한쪽 조건이 아예 안 떴는데, 결과가 "유령 0건"으로 나와서 좋은 결과로 읽을 뻔했음
- 정답 좌표를 사람 모델의 발밑으로 잡아서, 누운 사람만 오차가 1.12 m, 1.41 m로 보였음. 몸 중심으로 고치니 0.32 m, 0.54 m였음
- 카메라 RGB 8.7 Hz와 깊이 11.2 Hz가 어긋나서, 둘을 짝짓는 동기화기가 한 번도 짝을 못 지었음. 그동안 로봇은 아무것도 못 보고 있었음

## 정리

- 결과를 가장 크게 바꾼 건 알고리즘 개선이 아니라 카메라를 0.10 rad 숙인 것과 시간 예산이었음
- 로봇은 1대에서 2대까지 늘리는 게 확실한 이득이고, 그 뒤는 경로 탐색이 버티는지에 달렸음
- 한두 판짜리 결과는 몇 번이나 뒤집혔음. 판 수를 미리 정하고 두 곳에서 재현하는 습관이 가장 쓸모 있었음
